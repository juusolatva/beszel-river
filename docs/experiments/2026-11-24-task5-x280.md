# Frontend performance Task 5 (stable slots) on the X280 — 2026-11-24

**Result: kept, as one interleaved record per slot.** The first version (`ed31228`) wrote stream index
and size jitter to a second buffer in small runs. CPU work fell a little, but GPU time quadrupled in
about half the runs, which cost about 1.6 W on battery. Writing those two floats into the per-frame
instance record (`9ff633e`, eight floats per slot, one upload) removed that slow mode and kept the CPU
gain. The plan's acceptance rule (lower callback work, no regression in `dense-1000` or `draining`) holds
on AC. `9ff633e` was not run on battery.

GPU time is bimodal per run, never within one run. Full screen already switches between about 3 and 5 ms
on the baseline, which these runs leave unexplained. On top of that, `ed31228` has a slow mode of
8–11.5 ms. It hit 10 of 22 runs at 960×640 and 11 of 22 full-screen runs on AC, and 8 and 3 on battery;
no baseline or `9ff633e` run reached it. Only pools with many births per frame were affected:
`dense-1000`, `draining` and `drained` never were.

- **Not clock scaling.** The GPU clock (`/sys/class/drm/card1/gt_act_freq_mhz`, logged every 0.5 s
  through the battery pair) had a median of about 317 MHz in both modes.
- **Real power.** The battery's discharge rate (UPower's `history-rate` file) averaged 10.4 W in
  slow-mode heavy 960×640 runs, against 8.7–8.8 W in the other heavy runs of either commit.

## Cause

Short sequences on the sequence page, AC, 960×640, `dense-8000`, six runs each (30 s warmup, 40 s
measured), on `ed31228` with the renderer's upload switched by a local, uncommitted change:

| Variant | Change | GPU time per run (ms) |
|---|---|---|
| as committed | metadata in runs merged across gaps under 128 slots | 2.5, 2.5, 2.5, 11.4, 11.5, 11.5 |
| none (diagnostic) | no metadata uploads after the first frame; wrong colours and sizes | 2.5, 2.4, 2.6, 2.2, 2.4, 2.5 |
| span | dirty metadata range in one call per frame | 4.1, 2.8, 4.0, 2.9, 3.0, 4.1 |
| whole prefix | all metadata through `drawCount` every frame | 2.8, 4.2, 4.3, 2.9, 4.1, 4.2 |
| orphan | fresh storage for the instance buffer every frame | 11.4, 1.7, 7.8, 11.3, 11.3, 11.3 |
| interleaved (8 runs) | stream index and size in the instance record, one upload | 2.6, 2.6, 2.6, 2.4, 2.4, 2.6, 2.6, 2.6 |

So the metadata uploads caused it, and the number of calls mattered more than their size. The same
variants run round-robin on the bare benchmark page (`gpu-benchmark.html`, 30 runs) never entered the
slow mode, so short benchmark-page runs cannot show it. Why the sequence page provokes it (it holds a
screen wake lock and has more DOM) was not tested.

6 per slot through `drawCount` plus births, and `9ff633e` uploads 8 per slot through `drawCount`.

In a draining or rotating pool the drawn prefix spans holes, so `9ff633e` uploads more than the
baseline there. Its callback work in those workloads is still no higher. Its full-screen `rotation`
runs all landed at about 5 ms of GPU time, which is the baseline's upper mode.
