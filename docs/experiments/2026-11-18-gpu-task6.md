# GPU prototype, Task 6 paired runs — 2026-11-17/18

**Decision (user, 2026-11-18): keep for further evaluation.** The GPU backend meets the
[keep threshold](../superpowers/plans/2026-11-13-gpu-prototype.md#task-6-measure-and-decide)
on the X280 at both viewports and power modes and on the phone at full screen. It misses it in one phone
cell (960×640, `dense-8000`, p95). Every gated run passed occupancy parity, and all final states matched their validation replays: the complete state for CPU runs, and active flags, stream slots and generations for GPU runs (positions and other float values are not compared, as the validation protocol specifies). This supports a separate production proposal; it authorizes no production migration.

**Note — 2026-11-28:** the phone rows were measured at a non-production size. `test/gpu-sequence.html` had no `<meta name="viewport">`, so the phone's Chrome laid it out 980 CSS pixels wide: "full" is 1470×2942 and "960×640" 1440×960 framebuffer pixels, where the page itself (which has the tag) renders about 540×1200 in portrait. Simulation and submission work does not depend on the size; trail fill, frame intervals and missed periods do. The X280 and desktop rows are unaffected.

The phone is where cadence changes. At 10,000 particles the CPU path misses about a fifth of
all display periods (p95 interval 33.5 ms), and the GPU path almost none. The X280 and desktop hold
cadence on both backends, so there the gain is CPU headroom only.

On the phone, callback work includes more than particle stepping. With no particles (`drained`)
the CPU backend still spends 6.2–6.4 ms at full screen and 9.9 ms at 960×640, and the GPU
backend 6.8–6.9 and 10.5 ms. That cost is the flow field, stream easing and the GL calls both
backends make. At full screen it is about two-thirds of the GPU path's 9.8 ms. Why the
960×640 canvas costs more than full screen on the phone was not investigated; it persisted
after the battery reached 100 %, so charging heat does not explain it.

## Sparse, draining and drained runs

Frame-interval p95 does not regress anywhere: the phone stays at 16.8 ms on both backends, the
X280 at 16.7 ms and the desktop at 8.4–8.5 ms. Callback work depends on the workload. With no particles
(`drained`) the GPU backend's median and p95 are 0.1–0.7 ms higher on the phone and the X280, because it always simulates and
draws all 10,000 slots. In `draining` its median is 0.2–0.9 ms higher, but its p95, set by the
populated phase, is 4.5–9.6 ms lower. In the sparse `dense-1000` run the GPU backend is cheaper on the X280 (median
0.4–0.6 ms and p95 0.6–1.0 ms lower); on the phone its median is within −0.4…+0.2 ms at full screen and its p95 about 9–10 ms
lower:

| Set | Workload (full screen) | Callback median CPU / GPU | Callback p95 CPU / GPU | Missed CPU / GPU |
|---|---|---|---|---|
| Phone, battery | dense-1000 | 8.9 / 9.1 | 21.2 / 11.8 | 33 / 1 |
| Phone, battery | draining | 7.1 / 8.0 | 20.8 / 11.4 | 113 / 2 |
| Phone, battery | drained | 6.4 / 6.8 | 8.9 / 9.5 | 1 / 2 |
| X280, battery | dense-1000 | 2.3 / 1.7 | 3.1 / 2.3 | 0 / 0 |
| X280, battery | draining | 1.1 / 1.4 | 7.5 / 2.2 | 0 / 0 |
| X280, battery | drained | 1.0 / 1.3 | 1.3 / 1.7 | 1 / 2 |

The other sets follow the same pattern; the exported ledgers have every cell. One exception:
on the charging phone at 960×640, the GPU's `dense-1000` median is 3.7 ms higher, 12.9 against 9.2 ms,
while its p95 is lower, 16.4 against 25.1 ms. The phone's CPU `dense-1000` and `draining` p95 values (21–25 ms) are far above their
medians, unlike on the X280. That is consistent with the scheduler keeping a light load on
slower cores, but it was not investigated.

## Adaptive budget and its schedule replayed

The CPU adaptive discovery run shows what the production budget does with the CPU path. On the
phone it cuts the limit to 2,500 (960×640, intensity ×2.00), 3,277 (full, charging, ×1.75) and
4,096 (full, battery, ×1.56). On the X280 and desktop it stays at 10,000. Replaying those
schedules through both backends:

| Set | Viewport | Final limit | CPU / GPU callback median | CPU / GPU callback p95 |
|---|---|---|---|---|
| Phone, charging | 960×640 | 2,500 | 11.4 / 13.0 (+14 %) | 13.7 / 17.4 (+27 %) |
| Phone, charging | full | 3,277 | 11.7 / 9.6 (−18 %) | 14.1 / 12.3 (−13 %) |
| Phone, battery | full | 4,096 | 11.8 / 9.7 (−18 %) | 14.2 / 11.9 (−16 %) |
| X280, both | both | 10,000 | 6.4–7.4 / 1.5–1.7 | 7.9–8.9 / 1.8–2.3 |

So at the particle count the phone actually shows today, the GPU path saves less (and costs more
at 960×640). Its value on the phone is showing 2.5–4× as many particles at about the same
callback cost and full cadence. That needs a GPU-side budget, which the
prototype does not have: it replays the CPU's decisions.

## Occupancy and lifecycle

- Parity: 62 gated runs per full set (31 for the phone on battery), all passed. In all 387 runs the
  final states matched their validation replays: the complete state for CPU runs, and active flags, stream slots and generations for GPU runs (positions and other float values are not compared, as the validation protocol specifies).
- Per-stream differences (reported, not gated): in steady runs (dense, discovery, schedule
  replays) at most 17 streams in a window fall outside their own bound. In rotation all 32 do, which is
  expected: the GPU claims replacement slots later (Task 5's 14.1 s drain deadline).
- Time from removal to zero live particles in the draining and drained runs: the GPU replay is
  0.23–0.52 s later than the CPU replay (median 22.2–22.4 s CPU, 22.6–22.7 s GPU). This matches the
  drain taper and deadline already accepted in Tasks 4 and 5.
- Rotation runs end 20 s after the river is removed at 70 s, before it reaches zero, so they have
  no time to zero. The 1 → 4 → 32 expansion happens 5–10 s into the 30 s warmup, so no
  expansion was timed.

## Power, heat and memory

Not measured. Thermal state was not recorded. The battery level each run started at gives a
rough hint only: 1 % resolution, and each interval also contains the untimed validation replays
of both backends.

- Phone on battery: 12 % over 111 minutes of CPU runs (6.5 %/h), 8 % over 114 minutes of GPU
  runs (4.2 %/h).
- X280 on battery, without the recharge pause: 43 % over 98 minutes of CPU runs (26 %/h), 38 % over 94 minutes of GPU runs (24 %/h).

The JS heap was 2.5–3 MiB at the median on the phone and the X280, and 6.9 MiB on the desktop, with no difference between
backends; occasional samples up to 20–31 MiB come from garbage-collection timing. GPU memory was not measured.

## Open items

- The phone 960×640 `dense-8000` p95 miss (−11 %, overlapping ranges).
- No GPU timing on the phone; no power or thermal measurement on any device.
- No native GPU budget: the prototype only replays CPU decisions, and it still simulates and draws all 10,000 slots after a limit drop.
- Expansion was never timed; rotation runs never drain to zero within the measured window.
- The remaining CPU cost on the phone (flow field, stream easing, GL calls; about 6 ms per callback
  at full screen) is untouched by the GPU path.
- The CPU reference is the current CPU path, not the "optimized CPU version" the milestone
  names: interleaved flow sampling and smaller instance uploads are still unimplemented.
- The run page's estimate of about 3 hours per set was too low on the phone (8.2 h for 86 runs);
  untimed validation with a readback after every step is slow there.
